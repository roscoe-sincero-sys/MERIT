MERIT Usability Audit

Can someone new to MERIT find where to start, act correctly at each step, and know when they have finished? Mostly yes. The places where they cannot are concentrated in a few high-traffic screens.

  • Auditor: Claude Code, Anthropic's AI coding assistant (model Claude Opus 5.5)
  • Date: Nov 2, 2026
  • Build: main @ 8b03204 (PR #146), local demo database
  • Type: evaluation only; no code changes, no records saved

A. Executive summary

Overall: MERIT is a well-built, consistent public-health application. Its navigation now groups features by job and shows each role only what it may use. Forms validate on the server with clear, focused error summaries. Automated accessibility testing found almost nothing. A trained user will be productive quickly.

Where it falls short: a first-time user will hesitate in a few dense screens, in the ones staff use every day. Most problems come from showing everything at once, or from a default that points the user the wrong way. Few come from missing features.

Major strengths (verified)

  • Accessibility (automated): axe-core reported no violations on 34 screens as the supervisor, the same as the administrator, and one as the county case manager, against WCAG 2.0, 2.1 and 2.2 A and AA rules.
  • Reflow: no page scrolls sideways at 768 or 390 px; at 1024 px and below the header folds behind a Menu button.
  • Navigation: grouped and scoped to each role, and keyboard-operable (Enter opens, Escape closes and returns focus). Most screens mark their place in it.
  • Error recovery: clear validation. Error summaries take focus and link to each field. When a session ends mid-form, the draft is kept.
  • Guidance: a search-first pattern prevents duplicate people. First-time authenticator setup is detailed and works.

Major weaknesses

  • Work queues: the daily task list is hard to read. Its most useful column is 116 px wide, so 15 tasks fill a 4,700 px page (UX-01, UX-07).
  • Held records: the group correction starts on Last name whatever the cause, inviting a wrong bulk correction (UX-02).
  • Case page: it shows every form at once, including Override and a red Close case (UX-06).
  • Recovery codes: they can be skipped by navigating away, and they are never shown again (UX-03).
  • Stored data: a data defect puts lab units inside addresses in tasks (UX-04).

Most important opportunities:

  1. Make the task list readable: put the detail under each task title, and use cards on phones.
  2. Make every bulk correction start from the field that caused the hold, and name that field in the confirmation.
  3. Put rarely used, high-stakes case actions behind a button.
  4. Keep the recovery-code step from being skipped.

Items 2 and 4 are quick wins. Items 1 and 3 are medium-effort changes to screens used every day.

Needs more testing: real users (no usability sessions were run), screen readers, WAVE, real phones, and every workflow that saves data (see limits).

Method, evidence and limits

I used the running application from a real browser (Microsoft Edge through Playwright) as eight demo roles, signing each one in for the first time. I combined that with inspection of the source code.

Roles tested

Supervisor, state administrator, county case manager (Baltimore City), intake clerk, epidemiologist, occupational investigator, city user administrator, and platform administrator.

What I ran

  • First-time sign-in: password, authenticator enrollment and recovery codes for all eight roles. The epidemiologist's run was captured step by step.
  • Navigation inventory: the structure, tab order and header axe results for every role.
  • Page sweep: 34 screens each as the supervisor, the administrator and the case manager. For each screen it recorded the heading, the current-location marker, back links, axe results (WCAG 2.0–2.2 A and AA), sideways scrolling at 1280, 768 and 390 px, console errors, and a full-page screenshot.
  • Eight task walkthroughs, including a session-expiry test.
  • Keyboard checks: the navigation groups, form fields and focus visibility.

Evidence labels

Each finding is labelled with how it was established:

  • Verified observed in the running application;
  • Code-inferred read in the source code, not exercised;
  • Potential plausible, and needs real-user testing.

Simulated first-time-user reasoning is not evidence from real users.

Not evaluated

  • Usability sessions: none with real people.
  • Accessibility tools: no screen reader (NVDA, JAWS or VoiceOver) and no WAVE, because neither tool was available in this environment. So screen-reader compatibility, announcements, and WAVE's errors, alerts and contrast checks are untested.
  • Zoom and devices: 200% and 400% zoom were approximated with narrow viewports (640 and 320 px CSS) rather than browser zoom. Real phones and tablets were not tested.
  • Workflows that save data: to keep the audit non-destructive, I didn't save a person or result, upload a file, release, reject or correct held rows, decide a match, complete, assign or dismiss tasks, log case activity, override or close a case, request extracts, mark one submitted, create a user, tenant or profile, or use "view as". These were walked up to the last step before saving, or inspected.
  • Background processing: the worker was not running, so I didn't observe background processing, such as an uploaded batch moving through validation.
  • Roles not signed in separately: cmbaltco, cmboth and countyadmin. Their permissions match roles that were tested.

Side effects (approved): I redeployed the local MERIT demo database from main, and reset and re-enrolled MFA for the eight audited demo users. Views, searches and sign-ins were written to the audit log as usual.

C. Cognitive walkthrough results

For each workflow I asked, at every step, the eight walkthrough questions: goal, action, control, action–result, feedback, progress, error recovery and next step. The tables keep the steps where an answer was no or uncertain. Breaks at names the first step where a first-time user is likely to stall or err.

StepWhat the user must doAssessment
1. Sign-inEnter user name and password, then ContinueClear. The page says a code will follow. Focus starts in User name.
2. Set up the authenticatorScan the QR code, or enter the key manually, then type the codeStrong. Numbered steps, a manual fallback and troubleshooting text. The required-field note sits oddly between steps 1 and 2.

The result page has a "Back to the person" link, but no navigation item is marked current, so the user's place is not shown (UX-08). In the results, two look-alike records (an "Ana Rivera" with no date of birth, and "Mia" and "Mya" Rivera with the same date of birth) carry no warning (UX-18, potential).

D. Detailed usability findings

20 findings: 2 high, 10 medium and 8 low. No critical issues: nothing stops a task from being completed. The severity reflects the impact on users and how often the workflow is used.

UX-01 High Verified

Work queue task details are unreadable in the grid

Affected
Work queues (Angular), task grid, every role with task.view
Problem
The Detail column, which explains why the task exists and what to do, is squeezed to 116 px and runs past the right edge of the grid. Each row grows to 150–200 px, so a page of 15 tasks is about 4,700 px tall. Task titles wrap word by word.
Evidence
At 1280 px: grid scrollWidth 1006 vs clientWidth 936; Detail header 116 px wide; page height 4,705 px (supervisor, demo data). Screenshot in C6.
Why users struggle
The user must scroll sideways, or open each task's case, to learn what the task asks. Scanning for the next job becomes reading a long, narrow column.
Recommendation
Show the detail as a second line under the task title (two lines, then "more"); give Task and Detail flexible widths and fix the others to their content; keep Detail out of the narrow column set. On phones, see UX-07.
Expected benefit
Read and choose tasks without scrolling sideways; about 3× more tasks on one screen.
Complexity
Medium
Heuristic / criterion
Nielsen 6 (recognition rather than recall), 8 (minimalist design)
UX-02 High Verified

Held-record group correction starts on the wrong field

Affected
Held records → Correct this cause
Problem
Whatever the chosen cause (missing date of birth, unknown test code, unknown unit), the Field list starts on "Last name". Correct entire group applies the value to every row in the cause, sender and batch, and its confirmation ("Apply this correction to all 4 rows…") doesn't name the field.
Evidence
Observed for "Missing date of birth": Field = Last name. Code: the select lists the file fields in fixed order with no selection tied to the cause (held.page.ts).
Why users struggle
A first-time user types the date and presses the obvious button, writing a date of birth into Last name on every row. The bulk action amplifies the mistake.
Recommendation
Preselect the field that matches the cause (missingDob → Date of birth, unknownTestCode → Test code, unknownUnit → Unit of the value, and so on); show the field, value and row count in the confirmation; offer "Correct and release".
Expected benefit
Removes the most likely bulk data-entry error in intake.
Complexity
Low
Heuristic / criterion
Nielsen 5 (error prevention)
UX-03 Medium Verified

Recovery codes can be skipped by navigating away

Affected
First sign-in → Save your recovery codes
Problem
The recovery-code step shows the full navigation and header search. The session is already complete, so any menu link leaves the step without acknowledging the codes, which "will not be shown again".

E. Workflow simplification recommendations

Step counts are user actions: clicks, field entries and confirmations. Fewer is not automatically better. Each proposal also removes a decision or an error opportunity.

E1. Correct a group of held rows (UX-02)

Current: 8 actions, 1 likely error
  1. Open Held records
  2. Choose the cause
  3. Change Field from Last name to the right field
  4. Type the value
  5. Correct entire group
  6. Confirm
  7. Select the rows

G. Overall usability scorecard

Scores come from the evidence above. 10 means a new user succeeds without hesitation, and 5 means frequent hesitation or rework. No category lacked evidence, but Accessibility is provisional.

Navigation intuitiveness
8/10

Grouped, role-scoped menus; consistent placement; keyboard support. Points lost for unmarked locations on some screens and the Audit log being hard to find (UX-08).

Workflow efficiency
6/10

Find-and-open flows are short (4 steps), but the daily task list needs sideways scrolling (UX-01), held corrections add steps and risk (UX-02), and adding a person requires retyping (UX-10).

First-time user experience
7/10

Sign-in and enrollment are clear and detailed; Home orients. Recovery codes can be skipped (UX-03), and domain jargon (ORU^R01, rule tiers) appears unexplained.

Ease of learning
6/10

Screens explain their purpose in a sentence, but there is no in-app help, and dense pages (case, queue, held) need practice to read.

Visual clarity
6/10

USWDS gives a clean base; the queue grid, the case page and duplicated lists reduce clarity, and primary actions are sometimes the wrong ones (UX-06, UX-12).

Consistency
7/10

Consistent components and terminology; remaining raw codes and date formats (UX-14), and different permission messages in the two front ends (UX-09).

Error prevention and recovery
7/10

Strong validation, focused error summaries, kept drafts on session expiry, confirmations on bulk actions; let down by the held field default and the extract action styling.

Accessibility (provisional)
8/10

axe: one violation in 102 page scans across three roles; reflow at 390 px; keyboard-operable navigation with visible focus. No screen-reader or WAVE testing was possible, so this score is provisional.

Overall usability
7/10

A capable, consistent application that trained staff will use well; a handful of targeted fixes to the daily screens would make it markedly easier for newcomers.
